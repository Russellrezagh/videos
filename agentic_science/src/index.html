Prologue

Three reports from the field

In 2026, two researchers published three detailed accounts of scientific work with Claude agents. Their lessons are the raw material of this page. We quote them exactly and mark them Reported.

Matthew D. Schwartz · Anthropic · 23 March 2026

Vibe physics: The AI grad student

A Harvard physicist supervised Claude Code through a real calculation in quantum chromodynamics: the resummation of the C-parameter Sudakov shoulder. The work became a paper (arXiv:2601.02484).

  • “There were 102 separate tasks across seven stages.”
  • “Claude maintained a tree of markdown files—one summary per stage, one detailed file per task.”
  • “…there was a serious error at the very beginning: the factorization formula was wrong.”
  • “When conventions are non-standard, it constantly reverts to textbook defaults even if you force it to write the conventions down and stick with them.”
  • “Claude had been adjusting parameters to make plots match rather than finding actual errors.”
  • “It says ‘verified’ when it hasn’t actually checked.”

His CLAUDE.md rule “NEVER use phrases like ‘this becomes’ or ‘for consistency’ to skip steps. Either show the calculation or say ‘I don’t know.’”

Lesson for us Task structure and durable notes help. A polished result and a self-reported check prove nothing.

Matthew D. Schwartz · Anthropic · 1 October 2026

Claude-shaped science

BootLoops is an open-source harness of reusable computational tools. Two of its results are in biology: evidence for gene conversion in “5.7 billion pairs of nearby mutations” from the 1000 Genomes Project, and tree-species turnover on Barro Colorado Island “4.5 times faster than neutral theory allows.”

  • “I insisted that Claude both use old tools and build new ones, so that the harness would grow.”
  • Separate sessions for each project, “plus a master session that coordinates the others, allocates compute, and validates results,” and sessions for “checking and rechecking results as an adversarial referee.”
  • “I had Claude periodically organize its files and consolidate them, so it always had access to the latest version of the plan.”
  • “I always ask to see plots. Even with all the monitors I set up, I’ve found the automated checks still can’t be trusted.”

Lesson for us Build tools, not grinds. Keep the plan in files that survive compaction. Review in a separate session. The scientist supplies the taste.

Siddharth Mishra-Sharma · Anthropic · 23 March 2026

Long-running Claude for scientific computing

An agent built a differentiable cosmological Boltzmann solver in JAX over several days. The target was “0.1% against CLASS”, an established reference code.

  • A progress file held “current status, completed tasks, failed approaches and why they didn’t work.”
  • The reference code served as a test oracle. The agent committed after each unit of work: “Run pytest tests/ -x -q before every commit.”
  • A gap: “for a while it was only testing the code at a single (fiducial) parameter point.”

Lesson for us An oracle makes progress measurable. Test coverage must span the parameter space, not one point.

What this page adds

Proposed The three accounts come from physics. We move their lessons to computational biology, and we make each lesson executable. One small, real problem carries every idea: which tree do four DNA sequences support?

The project name is QUARTET. Its week of work, its file layout and its agents are our construction. The code, the checks and the numbers are real. You can run all of them on this page.

Chapter 1

Name the things before you build them

Before you write code, write down the nouns. A shared vocabulary is the first convention of a project. It also shows where each thing lives, and so how each thing can be lost.

Fifteen entities carry the whole method. They form a loop: a question becomes tasks, tasks become code and runs, runs become evidence, and evidence supports or rejects claims that answer the question. The scientist sits in the centre. Select an entity to see its definition, an example from QUARTET, and the kind of state that holds it.

Rule · One word, one meaning

Use one term for one concept. Use it in code, in files and in prompts. If two words name one thing, an agent can treat them as two things. If one word names two things, an agent can mix them.

ASD-STE100 applies this rule to its vocabulary. A convention file applies it to symbols and units. In QUARTET the most important instance is one phrase: branch length means expected substitutions per site. Chapter 9 shows what happens when it drifts.

Chapter 2

The science: Project QUARTET

Four DNA sequences come from four species, A, B, C and D. Their shared history is a tree. For four taxa there are only three unrooted trees. The project asks which one the data support, and how sure we can be.

The trap

In QUARTET, species A and C evolve fast. Their branches are long. Long branches collect many changes, and some of those changes match by chance. A method that counts shared changes can then join A and C, although they are not relatives. Joseph Felsenstein described this failure in 1978. It is now called long-branch attraction.

History Reported

Microsporidia are fast-evolving parasites. Early trees from ribosomal RNA placed them near the base of the eukaryotes. Later analyses placed them with the fungi, and long-branch attraction is the usual explanation for the early result (Capella-Gutiérrez et al., 2012). QUARTET does not analyse microsporidia. It reproduces the mechanism with simulated data.

The data

The page simulates an alignment on the true tree, AB|CD. Below are the first 72 sites. Each column is one site. Colours mark the four bases.

The model of change

The Jukes–Cantor model (JC69) is the simplest model of DNA change. Substitution events occur at random along each branch. Each event replaces the base with one of the other three bases, with equal probability. For a branch of length t, the chance that a site shows the same base at both ends is

P_{\text{same}}(t) = \tfrac14 + \tfrac34\, e^{-\mu t}, \qquad P_{\text{diff}}(t) = \tfrac14 - \tfrac14\, e^{-\mu t}\ \text{for each other base.}

Convention C-1 · Branch length

Branch length t is the expected number of substitutions per site. This convention sets \mu = 4/3. Other textbooks use other time units and other constants. Do not copy a formula without its unit.

Two methods

Parsimony

Choose the tree that needs the fewest changes. Fitch’s algorithm counts the minimum number of changes per site on each tree. It is fast and it needs no model. That is its strength and, here, its weakness.

Maximum likelihood (ML)

Choose the tree and branch lengths that make the data most probable under the model. Felsenstein’s pruning algorithm computes each site likelihood. For a quartet with cherries (a,b) and (c,d) joined by an internal branch e:

L_{\text{site}} = \sum_{x}\pi_x\, P_{x s_a}(t_a)\,P_{x s_b}(t_b) \sum_{y} P_{xy}(t_e)\, P_{y s_c}(t_c)\,P_{y s_d}(t_d)

Here x and y are the unknown bases at the two internal nodes, and s_a \ldots s_d are the observed bases. The log-likelihood of the whole alignment adds the sites:

\ell(T,\mathbf t) = \sum_{c=1}^{15} n_c \ln L_c

Why only fifteen numbers

JC69 treats the four bases alike. So the likelihood of a site depends only on which taxa share a base. The 256 possible site patterns fall into 15 classes, the set partitions of four taxa. An alignment of any length reduces to 15 counts.

Engineering note

For one branch, each class likelihood is a straight line in z = e^{-\mu t}. A sum of logarithms of straight lines is concave. So a one-dimensional search finds the best branch length exactly. The kernel uses this structure, and test group G12 checks that the result is a true maximum.

In the repository

The science lives in two files. src/js/kernel.js holds the model, both likelihood routes, parsimony and the fit. src/js/lab.js holds the simulator, the checks, the studies and the run records. Both are pure: no page, no clock, no hidden randomness.

Chapter 3

Six kinds of state

Agentic work changes six kinds of state. Each kind lives in a different place, and each needs a different mechanism to protect it. Most confusion comes from using a mechanism for one kind of state to protect another.

Kind of stateWhere it livesExample in QUARTETWhat keeps it

A new conversation changes context. A new branch changes a reference. A new worktree gives another checkout. None of these, alone, proves that a scientific claim is correct.

Rule · Isolate what changes

Name the kind of state that changes. Isolate that kind of state. Use the smallest mechanism that does it.

Warning

Do not treat the word “workspace” as a promise. Applications use it for different boundaries. Find out what it isolates: files, processes, network access or credentials.

Chapter 4

Worktrees: two places to work

A repository stores history. A checkout holds files that you can edit. A worktree is one more checkout of the same repository, with its own HEAD, its own staging index and its own working files.

On day 1 of QUARTET, two subagents write the two likelihood routes at the same time. The stepper below follows their work through the repository. Proposed

ConceptWhat it isUse it whenIt does not guarantee
RepositoryThe version database and its referencesYou need the project’s historyInstalled packages, loaded context, a valid result
BranchA movable name that points to a commitYou need a line of developmentA second directory for parallel editing
WorktreeA checkout with its own HEAD, index and filesTwo tasks edit source at the same timeIsolation of processes, caches, ports, services or credentials
CloneA separate logical repositoryAnother machine or an independent lifecycleIgnored files, data, packages or local services
CommitA recorded tree, its parents and metadataYou need a reviewable checkpointUntracked files, data, runtime state, scientific truth
StashTemporary storage for work in progressA short interruption in one checkoutA durable record or an isolated task area
HEADThe commit a checkout is on, often through a branchYou must know what is checked outThat the files match that commit
IndexThe staging area for the next commitYou choose what a commit recordsIsolation from another writer in the same checkout

Mechanics that people forget

  • Linked worktrees share commit objects and most references. Each has its own HEAD, index and working files.
  • A commit in one worktree is visible to all of them at once. The files in the other worktrees do not change.
  • Git normally refuses to check out one branch in two worktrees at the same time.
  • A worktree can have a detached HEAD. Some harnesses start worktrees that way.
  • All worktrees share one stash list. Untracked files need an explicit option. Ignored files are not stashed.
  • A fresh worktree has no ignored files. A .env file or a local data cache does not follow you.

Procedure · Set up two parallel kernel tasks

  1. Make sure that the main checkout is clean.git status --short
  2. Create one worktree for the pruning task.git worktree add -b kernel/pruning ../q-pruning HEAD
  3. Create one worktree for the brute-force task.git worktree add -b kernel/brute ../q-brute HEAD
  4. Give each agent a task contract. List the paths that it owns.
  5. Tell each agent to write outputs only to results/<run-id>/.
  6. Review the diff and commit in each worktree.git -C ../q-pruning diff
  7. Merge the pruning branch in the main checkout.git merge kernel/pruning
  8. Merge the brute-force branch in the main checkout.git merge kernel/brute
  9. Run the full verification after the merge.node tests/verify.js
  10. Remove each worktree after its branch is merged.git worktree remove ../q-pruning

Caution

Do not assume that removing a worktree deletes its branch. It does not. Do not assume that deleting a branch removes its worktree. Do the two operations separately, and keep every commit and run record that you need.

In Claude Code Reported

claude --worktree feature-auth creates a worktree under .claude/worktrees/ on a new branch. Subagents can take isolation: worktree in their definition. A .worktreeinclude file copies gitignored files such as .env into new worktrees. The documentation states the scope plainly: worktrees “isolate file edits” (Claude Code docs). Other harnesses, such as Codex, offer similar modes.

Ask, enforce, verify

Three mechanisms look alike and do different jobs. Confusing them is a common source of false confidence.

Ask

Instruction file

CLAUDE.md or AGENTS.md. The agent reads it every session. It can still ignore it.

“Claude treats them as context, not enforced configuration.” Reported

Enforce

Hook or permission

The harness runs a command at an event and can block the action, whatever the agent decides.

Example: block a commit while tests/verify.js fails.

Verify

Check

A test of the result itself. It does not care what anyone intended. It reports what the code does.

Example: C9, the unit anchor.

Warning

Do not cite saved memory or a summary as evidence. Memory is helpful recall. A summary can omit the detail that matters. Cite the run record.

Chapter 7

One revision can produce many runs

A run is a function. Its output depends on the revision, the environment, the inputs and the seed. Record all four, and anyone can run it again. Miss one, and you can only hope.

\text{output} = f(\text{revision},\ \text{environment},\ \text{inputs},\ \text{seed})

Warning

Do not let two runs share an output path. Two worktrees can still collide on a port, a database, a cache, a GPU or an absolute path such as /tmp/study.csv. Give each run its own directory and its own resource budget.

Procedure · Make a run that someone can repeat

  1. Commit the source, or record the exact diff.
  2. Record the runtime and package versions.
  3. Fix the seed, and write it down.
  4. Create a new directory for the run. Use a unique run ID.
  5. Write the manifest before the results.
  6. Keep raw outputs separate from figures.
  7. Never overwrite a previous run.

Chapter 8

Tool, skill, agent, hook, harness, scientist

These six words name six responsibilities. A tool computes. A skill describes a procedure. An agent chooses actions. A hook enforces a rule. A harness runs and records. A scientist judges.

A skill, written down

A skill is a procedure that loads into context when a task needs it. Here is the one that QUARTET would use for its studies. Proposed

---
name: consistency-study
description: Run and report a phylogenetic consistency study. Use when a
  claim says that a method converges to a tree as data grow.
---
1. Fix the revision. Record the source hash. Refuse to run on a dirty tree.
2. Fix the scenario: branch lengths, pInv, true topology. Copy them into the manifest.
3. Use at least 5 sequence lengths, spaced by about x3, and at least 40 replicates each.
4. Derive one seed per replicate from the base seed. Never reuse a seed across lengths.
5. Run every method on the SAME simulated alignment.
6. Report the fraction that picks the true tree, with a 95% Wilson interval.
7. Also report the infinite-data answer from exact pattern frequencies.
8. If the finite-data trend and the infinite-data answer disagree, stop and report.
9. Never write "converges" for fewer than 3 lengths that agree.

The BootLoops lesson Reported

“Claude’s default approach seemed to be to try to grind through a long, multiday calculation rather than build a new tool that would make that same calculation take mere minutes.” QUARTET applies the lesson at small scale: the 15-class reduction and the concave branch search turn a slow fit into a tool that runs a full study in a second.

Chapter 9

The ladder of independence

A check is useful only if it can fail. It can fail only on errors that it does not share. We call this property independence. It comes in rungs, and each rung catches errors that the rungs below it cannot see.

Lab 1 · Two curves that agree almost everywhere

Mutant M1 is the day-3 bug. After compaction, the agent wrote the rate constant as \mu = 4, a value from a textbook that measures time in other units. Schwartz reports exactly this habit: Claude “constantly reverts to textbook defaults even if you force it to write the conventions down.” Reported So a written convention is not enough. A check must verify it. Compare the two curves. Move the slider.

Lab 2 · Mutation testing

Mutation testing breaks the code on purpose. A good check suite notices. QUARTET keeps four mutants, each with one change. The table shows the recorded result. Run the suite again in your browser to compare.

M1 · Rate-convention drift

Both routes share the constant, so they agree with each other. Rung 1 and rung 2 pass. Only the unit anchor, the published distance formula and the generative round trip reject it.

M2 · Dropped root prior

The pruning route forgets the factor 1/4 at the root. Pattern probabilities sum to 4. A cheap normalization check catches it.

M3 · Swapped same and different

A gross error. It fails the zero-length limit at once. Gross errors are common, and cheap checks catch them.

M4 · Skipped internal branch

The fast route ignores the internal branch. The result is still a valid probability model, so every rung-1 check passes. Only the brute-force route disagrees.

Acceptance needs a stated tolerance

|f_i - g_i| \le a + r\,|g_i|

The absolute floor a handles values near zero. The relative term r handles scale. QUARTET uses a = 10^{-15} and r = 10^{-10} for exact comparisons, and four standard errors for statistical ones. A tolerance is part of the claim. Write it down before you look at the result.

Rule · Agreement is not independence

Do not accept a result because two agents, two routes or two runs agree. Find out what they share. Add a check that does not share it.

Rule · Consistency beats confidence

    
Do not read a high replicate fraction as proof. Replicates measure sampling noise. They do not measure bias. Ask what the method does with infinite data.

  







  
Chapter 11

  
Correct code, wrong science

  
Every check in chapter 9 passes on the reference kernel. The code is right. Now give it data in which a fraction of sites never change, as in real genes. JC69 has no term for that. The model is wrong, and the code computes the wrong answer correctly.

  
In scenario B, 30% of sites are invariant, and the long branches are 0.75 substitutions per site. With infinite data, ML under JC69 picks AC|BD. ML under JC69+I picks AB|CD and recovers p_{\text{inv}} = 0.3 exactly. Study B in the harness shows the same at finite lengths.


  
Lab 5 · Ask the data whether the model fits

  
A goodness-of-fit test compares the 15 observed class counts with the counts that the fitted model expects. It is the first, automatic step of rung 4. It cannot choose the right model. It can tell you that the current one is wrong.

  

  

    
Rule · Test the model, not only the code

    
Check that the model can produce data like yours. Report the fit. Try a richer model. Ask an expert which processes the model leaves out.

  

  
Real analyses use richer models, such as GTR with gamma-distributed rates, or site mixtures, and choose among them with criteria such as AIC or BIC. Each step reduces one kind of misspecification. None removes the need for judgment.

Lab 6 · The task graph goes stale

  
Tasks depend on each other. When an upstream definition changes, every result downstream is stale until it runs again. Git cannot see this: a change to a convention can merge without a single conflict.

  
  

    
Rule · Stale by default

    
When a definition changes, mark every downstream result stale. Run each one again before you cite it. A conflict-free merge does not repair a changed scientific definition.

    Writing rules used on this page
    
  
      
    
    • Procedural sentences have 20 words or fewer. Descriptive sentences have 25 words or fewer.
      • 
    
    • One instruction in each procedural sentence. Imperative verb first.
      • 
    
    • Active voice, and simple present, past or future tense.
      • 
    
    • One word for one meaning. The glossary lists the terms.
      • 
    
    • Warnings and cautions start with the command, then give the reason.
      • 
    
    • Paragraphs have six sentences or fewer, and one topic.
      • 
  
    
  
    Type: Newsreader, IBM Plex Sans and IBM Plex Mono. Equations: KaTeX, rendered to MathML at build time. No tracking, no network calls from the labs.
